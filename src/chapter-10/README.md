# 多 Agent 协作与高级模式

前面九章让你掌握了 Notion Agent 从基础到进阶的全部核心能力。本章进入「架构师」层级——当你有多个 Agent 时，如何让它们协同工作，构建复杂的自动化工作流。

## 为什么需要多 Agent 协作

随着使用深入，你可能会发现一个 Agent 不够用：

- **职责膨胀**：Personal Agent 什么都做，指令越来越长，互相矛盾
- **权限冲突**：有些任务需要访问敏感数据，有些不需要
- **专业化需求**：不同任务需要不同的提示词和知识背景

解决方案：用多个专职 Agent 各司其职，由一个「调度中心」协调。

## 核心概念：Sub-thread（子线程）

Sub-thread 是多 Agent 协作的基础机制。一个 Agent 可以在对话中启动另一个 Agent 的子线程，等待它完成任务后获取结果。

### 工作原理

```
你 → Personal Agent → [创建子线程] → Custom Agent A
                                        ↓
                                    执行任务
                                        ↓
                    ← [返回结果文本] ←
```

关键特性：

- **同步等待**：父线程会暂停，等子线程完成后继续
- **独立上下文**：子线程有自己独立的上下文，不会自动继承父线程的对话历史
- **只返回文本**：父线程只能收到子线程的最终文本回复，看不到中间过程
- **副作用保留**：子线程中创建的页面、修改的数据库等操作会实际生效

### 使用方式

你不需要手动调用 API。只需要告诉 Personal Agent：

> 💬 "让周报助手帮我生成本周的周报"

Personal Agent 会自动创建一个子线程，把你的请求转发给「周报助手」Agent，等它完成后把结果带回来。

### 继续已有子线程

子线程可以被继续——如果你对上一次的结果不满意：

> 💬 "让周报助手修改一下，重点突出产品发布那部分"

Personal Agent 会在同一个子线程中继续对话，这样周报助手能记住之前的上下文。

## 多 Agent 协作模式

### 模式 1：Hub-and-Spoke（星型调度）

最常见的模式。Personal Agent 作为中心节点，按需调用各个专职 Agent：

```
                 周报助手
                   ↑
反馈分析员 ← Personal Agent → 文档助手
                   ↓
                数据分析员
```

**适用场景**：日常工作中需要多种类型的任务支持。

**示例对话**：

> 💬 "让反馈分析员分析上周的客户反馈，然后让文档助手把结果整理成一份报告"

Personal Agent 会依次调用两个 Agent，串联结果。

### 模式 2：Pipeline（流水线）

一个 Agent 的输出作为下一个 Agent 的输入：

```
数据采集 Agent → 数据清洗 Agent → 报告生成 Agent
```

**适用场景**：需要多步处理的复杂任务。

**实现方式**：在 Personal Agent 的指令中描述流水线步骤，或让用户在对话中逐步引导。

### 模式 3：Review（审核链）

一个 Agent 生成内容，另一个 Agent 审核：

```
写作 Agent → 审核 Agent → [通过/修改意见] → 写作 Agent
```

**适用场景**：需要质量把控的内容生产。

**示例**：

> 💬 "让写作助手写一篇产品更新博客，然后让审核助手检查用语规范和事实准确性"

### 模式 4：三省六部体系（高级案例）

这是一个真实的多 Agent 工作流设计，灵感来自中国古代的行政架构：

**设计理念**：
- **"皇上"（用户）**：只做方向决策和最终验收
- **"中书省"（Personal Agent）**：理解意图、制定方案、协调执行
- **"六部"（Custom Agents）**：各有专职——写作、分析、编程、审核等

**工作流示例**：
1. 用户说："我想写一本使用指南"
2. Personal Agent 分析需求，制定大纲
3. 调用「写作 Agent」执行各章节写作
4. 调用「审核 Agent」检查质量
5. 调用「排版 Agent」生成最终输出
6. 回报用户做最终验收

**优势**：
- 每个 Agent 指令精炼，不会互相干扰
- 权限隔离——写作 Agent 不需要访问财务数据
- 可独立迭代——改进审核标准只需要修改审核 Agent

## 子线程的限制

### 50 次调用上限

一个父线程最多创建 50 次子线程调用。超过后会报错 `max sub agents exceeded`。

**应对策略**：
- 合并请求：把多个小任务合成一次子线程调用
- 开新对话：如果一个对话用完了配额，开一个新的 Thread 继续
- 合理规划：复杂任务在开始前估算需要几次子线程调用

### 权限约束

- Personal Agent 可以调用任何自定义 Agent
- 自定义 Agent 之间的调用需要显式授权
- 未授权的跨 Agent 调用会被拒绝

> 💡 配置自定义 Agent 时，在集成设置中指定它可以与哪些其他 Agent 通信。

### 上下文隔离

子线程不会自动获取父线程的上下文。如果子 Agent 需要某些信息，你需要在指令中显式传递：

> 💬 "让数据分析员分析'任务跟踪'数据库，重点看本周完成率。上周完成率是 75%，需要做对比"

"上周完成率是 75%" 这个信息不会自动传递，需要你（或 Personal Agent）显式包含在发送给子 Agent 的消息中。

## 查看历史线程

了解 Agent 过去做了什么是优化的基础：

> 💬 "查看周报助手最近的对话记录"

Personal Agent 可以查询任何自定义 Agent 的历史线程列表，并深入调查某个具体线程的内容。这对于诊断问题和优化指令非常有用。

## 设计多 Agent 系统的最佳实践

### 1. 从简单开始

不要一上来就设计复杂的多 Agent 系统。先用 Personal Agent 完成任务，当你发现某类任务反复出现且有固定模式时，再抽象成专职 Agent。

### 2. 明确职责边界

每个 Agent 应该有清晰、不重叠的职责：

| Agent | 职责 | 权限 |
|-------|------|------|
| 周报助手 | 生成周报 | 只读任务数据库 |
| 反馈分析员 | 分析客户反馈 | 只读反馈数据库 |
| 文档助手 | 整理和格式化文档 | 读写文档页面 |

### 3. 保持指令精炼

每个 Agent 的 Instructions 只包含它需要知道的内容。不要把所有背景知识都塞进去。

> ✅ 周报助手指令："你是周报助手。从任务数据库获取本周完成的任务，按项目分组，每个项目最多列出3个要点。输出格式为..."

> ❌ 周报助手指令："你是周报助手。公司成立于2020年，主要做SaaS产品..."（不需要的背景信息）

### 4. 设计错误处理

子 Agent 可能失败。在 Personal Agent 的工作流中，考虑失败情况：

- 如果子 Agent 返回的结果不满意，可以重试或换个方式指导
- 如果子 Agent 无法完成任务（缺少权限、数据不存在），应该有回退方案

### 5. 监控和迭代

通过查看历史 Thread 了解 Agent 的实际行为：

> 💬 "查看周报助手最近的对话记录"

根据实际表现持续优化每个 Agent 的指令和配置。

## 实战案例：搭建团队知识管理系统

### 需求

自动化团队的知识管理：会议纪要自动归档、技术文档定期审核、新员工入职文档自动生成。

### Agent 设计

| Agent | 触发方式 | 职责 |
|-------|---------|------|
| 会议归档员 | 会议结束后手动触发 | 整理会议记录，提取行动项，归档到知识库 |
| 文档审核员 | 每月定时触发 | 检查知识库中过期的文档，通知负责人更新 |
| 入职助手 | 新员工数据库新增记录触发 | 根据岗位生成定制的入职文档包 |

### 实现步骤

1. 创建三个自定义 Agent，分别配置指令和权限
2. 为文档审核员配置每月定时触发器
3. 为入职助手配置数据库新增记录触发器
4. 会议归档员通过 Personal Agent 手动调用
5. 测试每个 Agent 的独立功能
6. 测试协作流程

## 本章小结

- **Sub-thread** 是多 Agent 协作的基础：父线程同步等待子线程完成
- **四种协作模式**：星型调度、流水线、审核链、三省六部
- **50 次上限**：一个父线程最多 50 次子线程调用
- **权限约束**：Personal Agent 可调用任何自定义 Agent；自定义 Agent 间需显式授权
- **上下文隔离**：子线程需显式传递所需信息
- **设计原则**：从简单开始、明确职责、精炼指令、处理错误、持续迭代

---

> 📌 **本章盲区声明**：多 Agent 协作是 Notion Agent 较新的高级功能，具体行为可能随版本更新变化。子线程的调用上限（50 次）和权限模型可能在未来调整。本章的设计模式基于当前能力总结，不代表官方推荐架构。「三省六部」体系是用户实践案例，不是 Notion 的官方功能名称。
